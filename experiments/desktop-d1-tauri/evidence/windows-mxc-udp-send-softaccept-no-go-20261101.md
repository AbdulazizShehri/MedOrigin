# MedOrigin D1 MXC TCP/UDP matrix: native Windows UDP soft-accept NO-GO

**2026-11-01 • NONPUBLISHING • SYNTHETIC ONLY • NO PHI • NO CLINICAL USE.**
This is a real native Windows run of a synthetic Rust probe, **not** the
MedOrigin GUI binary, not independent WFP/packet capture, not WebView2
broker/service qualification, and not a claim of total OS network denial.

## Exact host/environment and scope

- Authorized connected Windows 11 Home **26H2, build 26300.9818**, x64.
- Existing supported **Node 24.22.1**, offline cached
  `@microsoft/mxc-sdk@1.0.1`, Rust 1.97.1.
- Native MXC ProcessContainer `containment:{type:'process'}` with
  `egress.default='deny'`, `ingress.default='deny'`,
  `hostLoopback='deny'`; no MXC isolation warnings observed.
- The native probe is compiled once from
  `tests/windows-mxc-protocol-matrix-probe.rs`. The **same native binary**
  first attempts locally controlled TCP and UDP on 127.0.0.1/::1 without
  confinement (positive control). Reserved RFC5737 `198.51.100.7`
  and RFC3849 `2001:db8::7` targets are only used under MXC deny-all;
  no unrelated user process, account, real endpoint, DNS query or patient
  data is involved.
- The local UDP positive controls actually delivered exactly one
  datagram to each local listener. The contained negative trials compare
  the change against those authenticated local listener counters.
- The runner reports native synthetic socket results only.
  **No packet capture, WFP trace, or external UDP delivery observer**.

## Actual native results — twice, same policy

Observed consistently on two runs using the historical source harness
and its current new pure validator:

| Operation | MXC result | Source acceptance |
| --- | --- | --- |
| TCP IPv4 127.0.0.1 | `WSA10013` | Denied by socket API |
| TCP IPv6 ::1 | `WSA10013` | Denied by socket API |
| TCP IPv4 TEST-NET-2 | `WSA10013` | Denied by socket API |
| TCP IPv6 documentation target | `WSA10013` | Denied by socket API |
| **UDP IPv4 127.0.0.1** | **`SENT23`** | **NO-GO: send API succeeded** |
| **UDP IPv6 ::1** | **`SENT23`** | **NO-GO: send API succeeded** |
| **UDP IPv4 TEST-NET-2** | **`SENT23`** | **NO-GO: send API succeeded** |
| **UDP IPv6 documentation target** | **`SENT23`** | **NO-GO: send API succeeded** |

After subtracting the positive-control datagram:
`D1_MXC_CONTAINED_UDP4_LOCAL_DELIVERED=0`, same for UDP6.
This means no contained datagrams were observed by **those two
local listeners**. It does **not** tell us whether the OS dropped
a TEST-NET datagram at a network layer, whether a UDP broker
transmitted anything, or whether any DNS packet left the host.

The older harness correctly returned **exit 1** at the first UDP
`WSA10013` assertion, but only reported a generic
`UDP4_LOOPBACK did not demonstrate WSA10013 enforcement` failure.
The revised same-source harness returns **exit 1** with a precise
fail-closed reason:

```text
D1_MXC_PROTOCOL_NO_GO: UDP4_LOOPBACK send_to returned SENT23;
zero local delivery is NOT OS packet/WFP denial proof
EXPECTED_NATIVE_UDP_SOFT_ACCEPT_NO_GO_EXIT=1
```

**Do not treat UDP `send_to Ok(23)` as demonstrated network access or
as demonstrated WFP denial**. A successful datagram send call says
nothing conclusive about later routing, filtering or delivery. The
required packet-level observer remains unavailable as documented in
the separate [MXC capture E_NOTIMPL report](windows-mxc-capture-receipt-native-no-go-20261101.md).

## Additional real positive policy differential — hostLoopback

A **disposable local-only controlled variation** of the same source
harness changed just the native MXC request's per-run
`hostLoopback:'deny'` to `hostLoopback:'allow'`, keeping
`egress.default='deny'` and `ingress.default='deny'`.
The same Rust source and synthetic host-owned loopback listeners were
used. With the explicit loopback grant, Windows returned:

```text
TCP4_LOOPBACK=CONNECTED
TCP6_LOOPBACK=CONNECTED
UDP4_LOOPBACK=SENT23
UDP6_LOOPBACK=SENT23
UDP4_TEST_NET=SENT23
UDP6_DOC_NET=SENT23
D1_MXC_CONTAINED_UDP4_LOCAL_DELIVERED=1
D1_MXC_CONTAINED_UDP6_LOCAL_DELIVERED=1
```

**Key contrast:** full-deny had **0/0** contained UDP loopback
deliveries; allow-host-loopback had **1/1** deliveries to the
same kind of owned listeners. The original strict deny-only harness
correctly returned **NO-GO/exit 1** for this intentionally
permissive setting, first because the UDP listeners received actual
datagrams. This is a deliberately nonqualifying positive control
showing that the local packet observers are operational and sensitive
to that one MXC policy dimension. It is **not** a production sandbox
setting, WebView2 evidence, packet capture of documentation-target
UDP, or WFP/DNS provenance.

The temporary script for this controlled variation was **not
committed**; it was generated by changing only the single
`hostLoopback` value in the exact committed test script. No
machine-global firewall/Edge setting was changed; no patient data,
external listener or real DNS operation.

## Concrete code/test changes

- `tests/windows-mxc-protocol-matrix-verdict.mjs` introduces a **pure,
  fail-closed** verifier for exact eight socket markers, explicit TCP
  WSAEACCES, exact UDP WSAEACCES, unique bounded output, complete
  socket evidence, MXC clean warnings and exit, Rust acceptance sentinel
  and both independently measured local UDP receipt counts.
- A `SENT\d+` UDP result explicitly produces an explanatory
  **NO-GO**, even if `delivered4=delivered6=0`.
- `tests/windows-mxc-protocol-matrix-negative.mjs` uses the
  pure verifier instead of treating socket send output as packet
  attestation. No source policy relaxation, listener bypass,
  fake packet counters or all-network-green marker was added.
- `tests/windows-mxc-protocol-matrix-verdict.test.mjs` exercises
  false-positive/missing/duplicate/truncated rows, any TCP or UDP
  deviation, each of the four actual `SENT23` results, missing
  warning receipt, process timeout and leaked local datagrams;
  `windows-mxc-protocol-matrix-contract.test.mjs` binds the
  actual source path to the new verdict.
- Native Windows source/test run **34 PASS, 0 FAIL**. All mutations
  execute purely in-memory with no network calls. Separate source-only
  Windows CI is run and verified after this report.

## Remaining path to a justified offline release

The pre-Tauri primary-token gate and the previously qualified actual
four-fixture Tauri/WebView2 GUI runs in [Draft #797](https://github.com/AbdulazizShehri/MedOrigin/pull/797)
are distinct from this synthetic socket control.
The existing WebView2 background TCP evidence in
[issue #662](https://github.com/AbdulazizShehri/MedOrigin/issues/662)
remains a blocker. The separate EGM network design
(`docs/designs/D1_NETWORK_CONFINEMENT_EGM.md`) requires an
**authorized disposable Windows environment** with independently
observed negative packet/DNS/IPv4/IPv6/TCP/UDP flows, complete
broker/descendant attribution and exact policy/binary identity,
as well as independent security review.

Microsoft's MXC OS support guidance distinguishes native process
isolation from Learning Mode capture. On this 26300.9818 machine
`captureDenials` *preflight* was positive, but the actual
`StartLearningModeTraceWithOptions` returned
`HRESULT 0x80004001 (E_NOTIMPL)`. Neither transparent fallback to
legacy access-only recording nor a global firewall/Edge change is
acceptable as WFP packet evidence.

**Issue #662 remains OPEN. All release/security assertions remain
NO-GO.** No protected-main merge, installer, tag, release, online
service, clinical input or host-wide security policy mutation.
