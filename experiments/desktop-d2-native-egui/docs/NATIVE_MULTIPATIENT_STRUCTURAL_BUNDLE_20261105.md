# D2 native multi-patient, bounded fictional FHIR Bundle browser

**2026-11-05. Owner-private stacked Draft on #960. A substantial structural Workspace stepping stone, NOT production EHR, PHI, or complete FHIR R4 clinical validation.**

## Product capability

The previous encrypted-Core focused view accepted only two SHA-reviewed reports, each containing exactly **three** dummy resource identities from one imaginary patient. This independent, explicitly opted-in native Rust viewer can display **up to 48 FHIR-shaped resources across up to 16 fictional patients**, with group isolation, type facets, source-derived local reference graph, read-only record details, bounded navigation history and a clean source reset. This demonstrates navigation across a variable-sized FHIR Bundle rather than a hardcoded three-resource screen. The existing Windows test-only AES-256-GCM Core + source-attested/nonce-HMAC portable launcher remains unchanged and is not silently switched to this new untrusted pathway.

Use exactly `--synthetic-multipatient-bundle-stdin` with the canonical generated JSON bytes (not a file path or HTTP URL). The normal no-argument Desktop mode does not read stdin. The native reader has a **32,768-byte** cap for this flag only, and a five-second one-shot stdin deadline; original encrypted Core/single-source modes retain their **2,048-byte** bound. The generator `scripts/generate_fictional_multipatient_bundle.py` uses Python standard library only and emits stdout bytes without reading user files, external URLs or clinical records. It supports `--patients 1..16` and `--observations-per-patient 1..3` subject to 48 resources total. The committed eight-resource fixture has **2 Patients, 2 Encounters, 4 Observations**, separated into two complete independent reference graphs. Exact generator output is byte-for-byte compared with that fixture in offline source tests. 16 Patients with one Encounter and one Observation each make 48 resources; 49 resources reject.

## Strict structural admission rules

- Input must parse as **canonical minified sorted-key JSON** (a serde_json round-trip must produce the identical bytes), rejecting duplicated keys, trailing bytes, reordered/spaced ambiguity, excessive size and invalid JSON.
- The only top-level keys are `entry`, `meta`, `resourceType`, `type`. Resource type must be Bundle/collection with exactly one `meta.tag` entry containing the fixed fictional marker. A marker is **NOT** proof of a trustworthy sender, patient de-identification or clinical validity.
- Every Entry contains precisely `fullUrl` and `resource`; resource fields allow only `id`, `resourceType` and the applicable `{reference}` links. No names, birthdates, clinical observations, numerical measurements, notes, addresses, coded diagnoses, narrative text, attachments, medical history or arbitrary extensions. Types are strictly Patient, Encounter and Observation; identifiers use narrowly bounded `fictional-*-NNN` values; local references use fixed-shape numbered imaginary UUID URNs with unique IDs.
- All references must resolve within the same source Bundle; Encounter.subject must point to a Patient; Observation.subject to Patient and Observation.encounter to an Encounter **belonging to that same Patient**. Duplicate IDs, duplicate URNs, external URL/remote references, dangling refs and cross-patient encounter associations fail closed before any GUI window.
- Native in-memory browser selects a specific fictional patient group, optionally all, and has type facets All/Patient/Encounter/Observation. A group or type change clears prior selection and history. Only visible source identities may be selected. Outgoing/incoming relationships and Back use only admitted original resource references; unknown or hidden selections and invalid navigation state fail closed, clearing the source. Navigation history is bounded to 24 steps, never stored in Core/SQLite.
- No production cryptographic key, patient-data import, network, OS process spawn from GUI, clipboard, file picker or clinical treatment/documentation workflow. This is a **read-only, structurally restricted synthetic developer preview**, not a clinician-facing release.

## How to run privately

Build D2 with offline Cargo and do not publish the result. The real Windows/macOS native GUI tests use the exact reviewed fixture and pass bytes through a bounded stdin process; for a custom fake-only size, generate with e.g. `python -B scripts/generate_fictional_multipatient_bundle.py --patients 16 --observations-per-patient 1`. On a POSIX shell the bytes can be piped to the local reviewed native GUI with the explicit `--synthetic-multipatient-bundle-stdin` flag. On Windows PowerShell, do **not** pipe binary JSON through PowerShell 5.1 text transformations; pass generator bytes using Python `subprocess.Popen(..., stdin=PIPE)`. Never load actual patient files. Neither mode authenticates a remote sender or encrypts this particular preview.

## Mandatory NO-GO for production or clinical use

This is not a general-purpose FHIR R4 validator, encrypted transport, audited EHR import, FHIR server connector, real demographic/clinical record viewer, identity/RBAC/consent model, patient de-identification classifier, audited production cryptographic key store or signed installer. It intentionally rejects virtually all clinical FHIR payload content. The local fictional marker is self-asserted, and a fake-looking identifier does not prove data provenance. Preserve this as a **separate dev-only path** until production key management, authenticated transport, validated FHIR R4 profiles, privacy isolation, clinical and security review, OS/network restrictions, accessibility acceptance and dependency advisories are closed. No real patients, no public distribution, no merge to protected main, no release or notarization.
