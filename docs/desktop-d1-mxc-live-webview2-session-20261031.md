## Why #662 remains NO-GO

**Zero observed sockets in this short sampled interval is NOT zero egress.** The time-bounded `Get-NetTCPConnection` and `Get-NetUDPEndpoint` view can miss short-lived flows, DNS traffic, failed outbound attempts, kernel-brokered connections and processes that begin/end between the 250 ms samples. This experiment does **not** capture/attribute native WFP permit/deny decisions, packet-level IPv4/IPv6 TCP/UDP/DNS flows, OS-wide network brokers or WebView2 security update traffic. No hostile packet injection or actual external network requests were deliberately generated by this source-defined fixture-only app.

On this Windows host, the separate V1 `captureDenials` invocation previously reached `StartLearningModeTraceWithOptions` and returned **`E_NOTIMPL 0x80004001`** (Draft #765). Do not silently switch to a permissive capture mode, disable updates, or install a global shared-WebView2 firewall rule to claim isolation. Stronger native denial/packet events on a supported Windows build and cold-start/steady-state/restart/suspend/update/teardown testing are still required. This run **does not reverse** the previously observed external WebView2 TCP events recorded in #662.
